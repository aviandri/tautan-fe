## Top 5 causes, ranked by impact

### 1. The whole public page hydrates as a client component tree. Impact: about 1.1 s LCP, about 120 kB of JS

**Evidence.** `src/components/public/PublicPage.tsx` starts with `"use client"`. So do `BlockRenderer.tsx`, `ProfileHeader.tsx`, `ThemedBlocks.tsx` and every `blocks/*.tsx`. All renderers for every block type are statically imported in `BlockRenderer.tsx`, so every visitor downloads, parses and hydrates code for all ~20 block types. The full page data is also serialized a second time as RSC flight data: the HTML is 29 KB raw, of which about 16 KB is `self.__next_f.push` payload. The no-JS ablation drops LCP from 2.80 s to 1.72 s on the same page.

**Fix.**
- Make `PublicPage`, `BlockRenderer`, `ProfileHeader` and the static blocks (heading, text, link, image, divider, quote, testimonial, discount code markup) Server Components that emit plain HTML and CSS.
- Keep small client islands only where interaction is needed: copy-code button, countdown tick, form/email-signup submit, lightbox, share sheet, click tracking. Click tracking can be one tiny delegated listener, or `navigator.sendBeacon` from an island, instead of a per-block `onClick`.
- FAQ and collapsible folders can use native `<details>/<summary>` with no JS.
- `next/dynamic` the heavier islands (form, booking, lightbox) so they load only when the block is present.
- Target: framework (~101 kB) plus islands under 10 kB. That meets the 110 kB budget and should put LCP near the 1.7 s no-JS figure.

### 2. User images are served at full resolution. Impact: about 0.26 s LCP, 268 KiB wasted, worse on real 4G

**Evidence.** `MediaBlocks.tsx:32` and `ProfileHeader.tsx:56` render raw `<img src>` pointing at `:8080/uploads/<hash>.jpg`, with no resizing, `srcset` or modern format. The hero image is 1600x1600, 239 KB, displayed at 380x380 (Lighthouse estimates 231 KB wasted). The avatar is 600x600, 44 KB, displayed at 92x92, and it is preloaded (`<link rel="preload" as="image">`) at the top of the critical path. The image block has `loading="lazy"`, but at y≈826 px it is inside Chrome's lazy-load distance, so it downloads at t=136 ms alongside the JS. Ablation: `/vnoimage` is 2.94 s vs 3.20 s.

**Fix.**
- On upload (BE `uploads.go`), generate fixed-width variants (e.g. 96/192 for avatars; 400/800/1200 for blocks) in WebP/AVIF, and store the dimensions.
- Render `srcset` + `sizes="(max-width: 480px) 100vw, 440px"`.
- Alternatively, use `next/image` with `images.remotePatterns` for the uploads origin, or a custom loader.
- Serve the avatar at 2x the 96 px size, about 5 KB.

### 3. The YouTube iframe loads eagerly. Impact: TBT 16 → 96 ms median with spikes to 2–4.9 s, about 1 MB third-party, run-to-run variance

**Evidence.** `MediaBlocks.tsx:92` sets `loading="lazy"` on the iframe, but the block sits within Chrome's lazy-iframe distance, so `youtube-nocookie.com/embed/…` starts at 140 ms. It then pulls about 1 MB: `base.js` 478 K, `ytembeds` 156 K + 222 K, CSS 58 K, Roboto from `fonts.gstatic.com`, `google.com/js/th`, and `jnn-pa.googleapis.com`. Removing the block (`/vnovideo`) cuts TBT from 96 ms to 16 ms. It also removes the cold-run spikes (runs 1 and 4: 4,872 ms and 2,093 ms) that pulled the score to 26 and 65.

**Fix.**
- Use a click-to-load facade. Render a `<button>` with the poster (`https://i.ytimg.com/vi/<id>/hqdefault.jpg`, or a copy cached through the BE), a play icon and a fixed 16:9 box. Swap in the iframe (with `autoplay=1`) on click.
- Do the same for Vimeo and Spotify embeds.
- Optionally add `<link rel="preconnect">` to `youtube-nocookie.com` on pointerover.
- `BookingBlock` already uses this pattern (`P2Blocks.tsx:141`).

### 4. The root layout leaks dashboard dependencies into the public page. Impact: about 31 kB JS and 52 KB of High-priority fonts on the critical path

**Evidence.**
- **Geist Sans + Mono:** `app/layout.tsx` loads `Geist` and `Geist_Mono` via `next/font`, so every route, `/[username]` included, gets a `Link: <…22a5144ee8d83bca-s.p.woff2>; rel=preload` header. That puts 28.9 K + 22.9 K of fonts at High priority before the CSS, but the themed public page renders in the theme font (Outfit here).
- **React Query:** `app/providers.tsx` wraps everything in `QueryClientProvider` (chunk `4633`, 5.7 kB). The public page doesn't use React Query.
- **zod:** `components/public/blocks/ContactFormBlock.tsx:4,10-12` imports `zod` just to check name/email/message length and email format. The whole library ships (chunk `3509`, 25.2 kB gzip, plus a 100 ms long task).
- **Theme font found late:** `lib/theme/fonts.ts` uses `preload: false`, so Outfit (31.8 K) is found only after the CSS is parsed, at t=136 ms vs 77 ms for the unused Geist fonts.

**Fix.**
- Move the Geist fonts and `<Providers>` out of `app/layout.tsx` into route-group layouts, e.g. `app/(app)/layout.tsx` for dashboard/onboarding/auth and `app/(marketing)/layout.tsx`. Keep `/[username]` under a bare layout.
- Replace zod in `ContactFormBlock` with a few lines of manual checks, plus `<input type="email" required maxLength>`, as `form-validate.ts` already does for the `form` block.
- In `/[username]/page.tsx`, emit `<link rel="preload" as="font" crossorigin>` for the single font the resolved theme uses. Keep `preload: false` globally.

### 5. Image blocks have no intrinsic size. Impact: CLS 0.109 when an image is in the first viewport (budget 0.05)

**Evidence.** `MediaBlocks.tsx:32` renders `<img class="image">` with no `width`/`height`. CSS is `width:100%; height:auto` (`public.module.css:199`), with no `aspect-ratio`. On `/vnovideo` the image sits at y≈599. When it loads, the 380x380 box appears and pushes the discount card down. `layout-shifts` attributes 0.109 to `div.public_discount`, and `unsized-images` flags the `<img>`. `/perfdemo` scores 0 only because the video pushes the image just below the fold. Most creator pages have an image near the top, so expect field CLS to fail. Link thumbnails (`LinkBlock.tsx:106,140`) and the announcement image have the same issue.

**Fix.**
- Store `width`/`height` when uploading (the BE can read them when it generates variants, see #2), include them in block data, and render `width`/`height` attributes, or `style={{aspectRatio}}`.
- Until then, give `.image` a placeholder `aspect-ratio` (e.g. `1 / 1`) with `object-fit: cover`.

## Other notes (smaller)

- **N1. Public HTML is uncached dynamic SSR.** The response is `Cache-Control: private, no-store`. Every view waits for Next to call `GET /api/v1/public/{username}` before sending a byte. On localhost that is 40 ms; in production add the FE→BE hop plus DB time. Consider ISR or `revalidateTag` on publish/edit, and a CDN cache with `s-maxage` + `stale-while-revalidate`, so TTFB stays under 200 ms on 4G.
- **N2. Legacy polyfills** in `9855` (12 KiB, `Array.prototype.at`, etc.). Set a modern `browserslist` in `package.json`.
- **N3.** `app/[username]/not-found` chunk is loaded on every successful page view (tiny, 0.2 kB).
- **N4.** `POST /api/v1/public/{username}/events` fires a CORS preflight on every view. Use `navigator.sendBeacon` with a `text/plain` body (no preflight), or proxy through a same-origin Next route.
- **N5.** The favicon is 25.6 KB. Use a smaller `.ico`, or an SVG/PNG icon.

## Expected result if #1–#5 are fixed

Using the ablations as a guide, LCP should reach about 1.5–1.7 s (≈ the no-JS run minus Geist/zod/image contention), first-load JS about 105 kB, TBT under 50 ms with no cold-run spikes, CLS 0 regardless of layout, and a score in the high 90s. Re-run this exact setup afterwards to confirm. The seed and Lighthouse commands are below.

## What's left for the last 0.37 s (ranked)

1. **Framework JS still sits in Lighthouse's LCP graph (about 0.3 s).** react-dom (54 kB) + Next runtime (47 kB) are ~92% of first-load JS, and they're the same on every route. Little is left to cut in app code. Options, in order of effort:
   - (a) Keep the budget honest: add a CI check that fails if `/[username]` First Load JS goes over 110 kB. It is at 110 kB today, so the next island added to the shared chunk will break it.
   - (b) Keep islands out of the shared `2235` chunk. Push them into per-block `next/dynamic` chunks so they load only when the block exists, as `6688` already does.
   - (c) Watch Next.js for a smaller runtime (the 12 KiB of legacy polyfills in `9855` aren't controlled by `browserslist`).
2. **The theme font isn't preloaded (about 0.05–0.1 s, plus contention).** Outfit (32 kB) starts at 51 ms, after CSS parse, at VeryHigh priority, competing with the poster. Emit `<link rel="preload" as="font" type="font/woff2" crossorigin>` for the single resolved theme font in `app/[username]/page.tsx`. Or, since this is text and not LCP-gating with `display: swap`, use `font-display: optional` on the public page.
3. **4 render-blocking CSS files (about 0.08 s measured).** Merge them, or enable Next's `experimental.inlineCss` for the public route. Total CSS is 12.6 kB, which is a good fit for inlining.
4. **LCP poster sizing (small).** On high-DPR phones the browser picks `?w=1080` (17 kB AVIF) for a 380 px slot. Capping the effective density at 2x (e.g. `sizes="(max-width:600px) min(100vw, 420px)"` plus a 2x-friendly 800w variant), or `fetchpriority=high` only on the first above-fold poster, would shave a few kB and some ms. Note that a video near the top makes the poster the LCP element, so poster bytes now matter.
5. **Favicon 25.6 KB.** It loads at High priority during the LCP window. Use a 1–2 KB `.ico`, or an SVG `icon.svg`.

Not measured here: real-network TTFB. On localhost the ISR hit is 3–5 ms, but Lighthouse still models 456 ms for TTFB (simulated RTT). In production, the CDN/edge caching of the ISR response will decide how much of that 0.37 s remains.

## Reproduce

```bash
cd tautan-be && REVALIDATE_SECRET=x make dev & make seed-heavy     # prints http://localhost:3000/heavy
cd tautan-fe && pnpm install && REVALIDATE_SECRET=x NEXT_PUBLIC_API_URL=http://localhost:8080 pnpm build \
  && REVALIDATE_SECRET=x NEXT_PUBLIC_API_URL=http://localhost:8080 pnpm start
npx lighthouse@12 http://localhost:3000/heavy --form-factor=mobile --throttling-method=simulate \
  --only-categories=performance --output=json --output-path=run.json --chrome-flags="--headless=new"
# first run after `pnpm start` = cold; then 3 warm runs, take the median
```
